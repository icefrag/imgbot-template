# adb 后端每设备一进程(监督者形态)

2026-11-11 魔神2 三台熔断案(2h 长跑后 OCR 引擎 bad allocation 风暴 + worker 线程
集体卡死 55 分钟, 详见魔神2库 1b93b76)暴露单进程多线程形态的结构性缺陷: 共享的
原生库(ORT/cv2/adb shell)病了或卡死, 全部设备陪葬, 且卡在 C 调用里的线程
Python 层杀不掉。决定: adb 后端下每设备 spawn 一个子进程跑完整任务循环,
中控台(Fleet)降级为监督者——拉起、转发日志、两段式停止(stdin stop→超时
taskkill /T)、按退出码与日志静默(10 分钟)判熔断/卡死并标红躺平, 不自动重拉。
子进程内仍复用 Worker 线程机制不动; window 后端(潜影注入)保持线程形态不动。
状态与日志经 stdout 行协议(`@st`/`@log`)回传, 断管=进程死=天然存活信号。

## Considered Options

- OCR 推理服务化(独立 OCR 进程 + 超时客户端): 只堵 OCR 一个口, adb/cv2 等
  其他共享原生态仍一锅端, 否。
- 进程内自愈(重建引擎重试): 已并入 master 常态(止血), 但治不了卡死与进程级
  内存病, 只能当第一层防线。
- 加开关双形态并存: 否——双分支并行(master=线程态, proc-isolate=进程态),
  分支上进程是 adb 唯一形态, 不留开关债。

## Consequences

- 每进程各加载一份 OCR 模型(~200MB/台); 慢 OCR 并发闸从全局 3 发变每进程
  1 发(4 台峰值 8 线程, 16 核机有裕量; 兜底旋钮 ORT_INTRA_THREADS 2→1)。
- 停机语义: 优雅停止靠子进程轮询 stdin, 卡死由 taskkill 兜底, 本轮中途死
  由业务恢复链(登陆→恢复→军团)自愈。
- 全局参数(business.yaml)经 refresh_cfg 每轮重读传播, 弹窗改完下一轮生效。
- 双库分支配对纪律: 魔神2@proc-isolate ↔ imgbot-template@proc-isolate
  (editable 直链, 两边必须同步切)。
